The follow-up to [the first speedup batch](2026-11-11-speedups.md), same setup: Qwen3-30B-A3B (Q8_0) on `gx10-02`'s GB10 with `--gpu --yarn 4`, the repository's own text as the prompt, 2,048-token chunks. Scripts and logs are in [`2026-11-11-speedups-2/`](2026-11-11-speedups-2/):
- `run.sh`: benchmarks, goldens, 16k, and 128k;
- `drift.sh`: two f32 matmul kernels against each other at 16k;
- `first-try/`: the first version of the kernel, without input scaling (stopped during its 128k run).

## The changes

- **Q8_0 matmul on tensor cores** (`tf_tm_q8`), for more than 8 inputs.
  - A Q8_0 weight's 8-bit values are exact in f16, and each block's scale is applied after its 32 products.
  - Each input row is multiplied by a power of 2 that brings its largest value near the top of f16's range, then split into high and low f16 parts. Two mma products per step (weights by each part) keep results close to exact.
  - The power of 2 is undone once per output, so it costs nothing in precision.
  - Each block computes 64 weight rows by 64 inputs with 4 warps.
- **Row scales without a separate pass over the inputs.** For experts, the kernel that gathers each expert's inputs also finds each row's scale, and the SiLU step finds the scales for the down matmul. q, k and v share one pass (`tf_rowscale`).
- **One wait per GPU call for small transfers** (decode). Calls that move at most 1 MB copy through pinned memory asynchronously and wait once at the end, instead of once per copy. At 16k this saved under 1 ms per token, less than estimated.
- `attbench --mm` times the matmul kernels and checks them against a double-precision sum on the CPU; `--alloc host` puts the data in pinned memory.

`TF_MM_KERNEL=2` brings back the tiled f32 matmul, and `TF_MM_KERNEL=1` the first one.

## Matmul kernels on GB10

`attbench --mm` (`attbench.log`), for a 2048 x 2048 Q8_0 weight and 2,048 inputs, including copies in and out:

| Kernel | Time | TFLOPS | Off a double-precision sum |
|---|---|---|---|
| Tiled f32 | 2.09 ms | 8.2 | 1.35e-4 |
| Tensor cores, first try (no scaling) | 1.26 ms | 13.6 | |
| Tensor cores, scaled per block of 32 | 1.81 ms | 9.5 | 3.0e-5 |
| Tensor cores, scaled per row (final) | 1.36 ms | 12.7 | 3.0e-5 |

The first try had no protection against inputs above f16's range (65,504) and lost precision on small ones. Scaling per block of 32 needed lane shuffles in the inner loop, which cost a third of the speed. Scaling per row costs about 2% end to end: the 16k prefill took 17.1 s on the first try (`first-try/16k.log`) and 17.5 s on the final build.

## Pinned memory

On GB10, weights and the KV cache are read in place from ordinary memory registered with the GPU. `attbench --alloc host` tried pinned memory instead (`cuMemAllocHost`):

| | Registered | Pinned |
|---|---|---|
| Decode matmul, 65536 x 2048 Q8_0, 1 input | 160 GB/s | 223 GB/s |
| Prefill matmul, tensor cores | 12.7 TFLOPS | 8.0 TFLOPS |
| Decode attention after 131,071 positions (decode kernel) | 3.22 ms | 3.67 ms |
| Same, tensor cores with 64 rows | 3.46 ms | 2.72 ms |

Pinned memory helps some reads and hurts others, so the engine keeps registered memory.

## Generated tokens at 16k

Against the tiled f32 matmul, the final build's 8 generated tokens at 16k are not all the same: the first tokens that differ have logits 20.6 apart. The same happens between the two f32 matmul kernels, which only add in a different order (`drift-*.log`): the tokens differ, again with logits 20.6 apart. So this prompt reaches a near-tie that any change in rounding tips, and the tensor-core kernel is the closest of the three to an exact sum. The short goldens, where transformers is the reference, still match every token.

## Not done

- CUDA graphs: a decode step's tile tables and shapes change every token, and the measured saving from fewer waits suggests launches cost little.
- Prefill attention at 128k (421 s) is the remaining big cost. Its tensor-core kernel needs three products per step for its accuracy; a cache format with less to round (TASK-27) would allow fewer.
