# Any number of expert nodes (TASK-33, 2026-11-16)

Until now rank 0 talked to exactly one expert process. It can now route to up to 63 (the transport's rank field has 6 bits).

What changed:

- **`src/split.zig`** holds the split, moved out of `olmoe_run.zig` so `zig build test` can reach it.
  - Rank 0's `SplitMoe` has one link per peer. Each call goes to the rank that owns its expert, and rank 0 runs its own experts meanwhile. When a peer has no free ring slot, rank 0 drains results from every peer, so no side waits on another forever.
  - Prefetch hints (TASK-11) go to each peer with its own experts. Each peer grants its own capacity (TASK-17).
  - Results are added in (token, choice) order, as before, so the output does not depend on which rank ran a call.
- **Placement:** `--ranks N` sets how many processes a run has. Without a manifest, the experts are split into N equal ranges, rank 0 first. A manifest may name any rank below N.
- **Launching:**
  - `shm` and `rdma` fork N-1 expert ranks on one machine.
  - Across machines, each expert takes `--rank R --ranks N`, and the router takes one `--peer IP:PORT` per expert in rank order.
  - A `tcp:` or `rdma:` prefix picks a peer's transport, so one run can mix them.
- **Tracker (TASK-09):** with `--ranks N`, a router waits for N-1 healthy experts.
  - It orders them by the rank each announced, then by tracker id, takes each expert from the first of them that owns it, and holds the rest itself.
  - It refuses to route once any of them turns unhealthy.
  - Over TCP, a killed expert resets its socket before the tracker can say anything. On a lost link, the router now waits up to 2 s for the tracker's verdict, so it reports the refusal either way.
- **Live diagram and replays (TASK-16, TASK-16b):** step frames carry one call count per rank. The page draws rank 0 with its peers in a grid beside it, one link to each, with that link's packet rate.

Logs, scripts (`run.sh` on `gx10-02`, `tcp.sh` from the desktop), versions, and a 4-rank recording (`olmoe-shm4.jsonl.gz`) are in [`2026-11-16-nodes/`](2026-11-16-nodes/).

Setup:

- `gx10-02`, kernel 7.0.0-1019-nvidia, driver 580.178.04, Zig 0.17.0, nothing else running.
- The desktop's i7-12700K in WSL2, reached on the campus path (TASK-21) through `fwd.py` (TASK-22).
- Engine build `v0.2.0-alpha-35-gca800e5-n33` on both.

## Bit for bit with CPU experts (`bits-*.log`)

This is Qwen3-30B-A3B with every expert on the CPU and activations sent as f32: a 512-token prompt in 256-token chunks, then 16 greedy tokens. The one-process run saved its tokens and logits, and each split run compared against them.

| Run | Experts on rank 0 | Same 16 tokens and logits as one process | First token | Decode |
|---|---|---|---|---|
| One process | 128 | (reference) | 27.0 s | 1.42 tokens/s |
| 2 processes, shared memory | 64 | bit for bit | 300.1 s | 1.89 tokens/s |
| 3 processes | 43 | bit for bit | 218.2 s | 2.37 tokens/s |
| 4 processes | 32 | bit for bit | 174.2 s | 2.45 tokens/s |

The acceptance asked for 3 and 4 processes to match the two-process run; all three split runs also match one process.

Split prefill on the CPU is slow because the split runs one call at a time, on rank 0 and on its peers, where one process batches each expert's calls (TASK-12). That was already so with two processes. With the GPU, rank 0's experts and the peers' run on CUDA.

## The TASK-10 and TASK-24 checks over 3 and 4 processes

All runs use the GPU, f32 activations, and the goldens of TASK-10, TASK-12 and TASK-24.

| 3 processes on two machines over TCP | PASS, 5.05e-5, every token | PASS, 2.88e-4 | PASS, 2.88e-4, every token |

Each cell gives the worst logits error against transformers; "every token" means every generated token matched `generate()`.

The TCP run had three processes on two machines:

- Rank 0 and rank 1 on `gx10-02`.
- Rank 2 on the desktop's CPU, 1.5 ms away.

Rank 2 took a third of the calls: 7,297 of 22,912 for OLMoE, and 21,178 of 64,128 for Qwen3 with YaRN. It answered in 1.1 to 1.5 ms per call, against 0.1 to 0.2 ms for rank 1 on the Spark's GPU. OLMoE generated 7.9 to 9.1 tokens/s this way, against 22 to 30 tokens/s with all four processes on `gx10-02`.

## The tracker gathering 3 experts (`tracker-*.log`)

There is one tracker on `gx10-02`, and three expert processes start with `--rank 1`, `2` and `3` of `--ranks 4`. The router gets only `--tracker 127.0.0.1 --ranks 4`.

- **The run:**
  - The router waited for the three experts, took ranks 1 to 3 in the order they announced, and used 16 experts from each.
  - It passed the OLMoE checks (5.05e-5, every generated token), with 5,815, 5,709 and 5,382 calls to the three ranks.
- **A killed expert:**
  - A second run generated for up to 5 minutes. After 40 s, rank 2 got SIGKILL at 22:13:59.051.
  - The tracker marked it unhealthy, and the router stopped at 22:13:59.114, 63 ms later, after 41,668 calls to it: "refusing to route to rank 2 ... unhealthy in map v16, received 8 ms ago".
  - The other two experts saw their links close and exited.
