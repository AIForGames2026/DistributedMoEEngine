# Chat replays across three DGX Sparks, and the desktop (TASK-33, 2026-11-16)

These are two recordings for the public page, made with TASK-33's multi-node split. Both use Qwen3-30B-A3B (Q8_0) and `tools/ref/record_chat.py`: the same scripted three-turn chat as TASK-16's recordings, at temperature 0 with reasoning on and up to 500 tokens per reply.

Setup:

- **The Sparks are cabled as a hub.** `gx10-02`'s `rocep1s0f0` goes to `gx10-03`, and its `rocep1s0f1` to `gx10-01`. So rank 0 on `gx10-02` names a device per peer (`--peer rdma:IP:PORT@DEV`).
- **Rank 0:** on `gx10-02`, with the GPU. It holds attention, the router and its share of the experts, serves the chat, and records it.
- **Expert ranks** (experts split evenly):

| Recording | Ranks | Links |
|---|---|---|
| `chat-three-sparks.jsonl.gz` | 3: `gx10-02`, `gx10-03`, `gx10-01` | RDMA to both, GPU experts |
| `chat-sparks-desktop.jsonl.gz` | 4: the same, plus the desktop | RDMA to the Sparks; TCP to the desktop's i7-12700K in WSL2, on the campus path through `fwd.py`, CPU experts |

- **Build:** engine `v0.2.0-alpha-35-gca800e5-n33d` on rank 0, and `n33b` on the expert ranks, whose code did not change in between.
- **Activations:** FP8, the default.
- **Script:** `2026-11-16/chat.sh`. The folder also has rank 0's log for the four-rank run and its transcript, plus the Spark experts' logs.

The two chats give different replies. FP8 activations round differently depending on which rank runs an expert, and the first reply then took a different path: 423 tokens ending normally, against 500 tokens of reasoning cut off at the limit.

## Why both are slow, and how they play

**`gx10-01`'s GPU was shared.** Another lab member's model server runs on `gx10-01`, and its GPU was at 96% when checked right after these were recorded. Rank 0 waits for its slowest peer on every layer, so every step waited on `gx10-01`.

**The three-Spark recording.** An earlier run of the identical three-Spark setup, while `gx10-01`'s GPU was free, decoded at 27.5, 27.2 and 27.5 tokens/s. That run used the same model, ranks, placement and payload, and gave the same replies, token for token. Its first tokens came at 20.1, 0.54 and 0.54 s. Its recording was deleted by mistake before re-recording, so only those log figures remain. Contention therefore cost the recording about 16 times, and the page plays it at 16x by default.

**The four-rank recording.** It is bound by the desktop's CPU: about 1.4 ms per expert call there, against 0.05 to 0.06 ms on a Spark's GPU. A free `gx10-01` would have changed little. Three processes with the desktop over TCP decoded 2.3 tokens/s earlier the same day (`../olmoe/2026-11-16-nodes.md`). The page plays it at 4x by default, only to keep it watchable.

Both play at their real recorded times. Only the default speed differs, and the page's speed control changes it.

## Lessons from making them

- **Size experts against what a co-tenant grows into, not what `free` shows.** `gx10-01`'s server sizes itself at startup to 113.7 of its 115.3 GiB. During the first attempt, that server restarted at 18:03 while a 10 GB expert of ours was running there. Its own log shows no error, and memory pressure from our expert is the likely cause. Docker restarted it, and it was serving again within minutes.
- **Starting a remote process:** `cd DIR && nohup CMD &` keeps a subshell holding the SSH session open as long as CMD runs; `cd DIR; nohup CMD &` does not. Stopping the waiting local script did not stop its child shells on Windows. They resumed later, started listening-only experts, and overwrote three of this folder's logs (the three-Spark rank 0 log, its transcript, and the desktop expert's log), which were then removed. The recordings themselves were not touched.
- **Stopping a server:** a background job of a non-interactive shell ignores SIGINT, so `chat.sh` stops rank 0 with SIGTERM and waits for it to exit before stopping the experts.
- **Engine fixes:** making these turned up three bugs, now fixed. Per-peer RDMA devices were missing. A TCP link from an `rdma-router` got the RDMA ring size (256 slots against its expert's 64). And the server sent a split long prompts in one step, past `--max-step`.
