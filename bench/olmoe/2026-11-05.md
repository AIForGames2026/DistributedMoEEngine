# OLMoE-1B-7B forward pass split across two processes (2026-11-05)

TASK-10 acceptance run. `olmoe` (ReleaseFast) runs allenai's OLMoE-1B-7B-0924-Instruct (Q8_0 GGUF, the file from [`../storage/gx10-03-2026-11-05.md`](../storage/gx10-03-2026-11-05.md)) on three golden prompts and compares every position's logits, each layer's hidden state, and every routing choice with Hugging Face transformers' own `OlmoeForCausalLM` (float32, eager attention) running the same Q8_0 weights, dequantized ([`tools/ref/ref_olmoe.py`](../../tools/ref/ref_olmoe.py); reference file SHA-256 `5fb4943b...8b23549`).

Rank 0 holds the embedding, attention, norms, router, LM head, and experts 0 to 31 (3.94 GB); rank 1 holds experts 32 to 63 (3.42 GB). Per layer, rank 0 sends each (token, expert) pair owned by rank 1 as a dispatch packet and adds the combines back in a fixed order. About 2,600 of the 5,504 expert calls per run go to rank 1. Both processes load through the io_uring reader and check every expert against the `.tfsum` index.

The prompts: "The capital of France is" (5 tokens), a Python Fibonacci function (21 tokens), and a sentence about MoE routing (17 tokens). As a sanity check, the reference's greedy continuations are "Paris." and a correct `fibonacci(n-1) + fibonacci(n-2)`.

Hidden states match within 3.3e-4 after every layer in every run. Results are the same on x86 and ARM, so the target of at most 1e-2 is met with a wide margin. The two-process runs are faster than one process because the two halves of the experts run in parallel. The TCP run is bound by the relay's 33 ms round trip, paid once per layer (TASK-21).

## Payload encodings

OLMoE's hidden state is 2,048 values. The packet's payload holds 7,168 bytes, so F32 goes as two packets per expert call each way (chunk number in `flags`; [`docs/wire-format.md`](../../docs/wire-format.md)). FP8 (the wire format's default) and BF16 fit in one.

| Payload | Bytes per call each way | Logits max err | Hidden max err | Top-1 | Experts chosen identical |
|---|---|---|---|---|---|
| F32 (2 packets) | 8,192 | 3.77e-5 | 3.3e-4 | 43/43 | 5,504/5,504 |
| BF16 | 4,096 | 0.018 to 0.35 | 0.011 to 0.022 | 43/43 | 5,503/5,504 |
| FP8 E4M3, E8M0 per 32 | 2,048 + 64 scales | 0.60 to 2.09 | 0.36 to 0.42 | 43/43 | 5,437/5,504 |

The lossy encodings miss the 1e-2 logits target, because each remote expert call rounds the hidden state twice (dispatch and combine), across 16 layers. The local run, with no rounding, is at 3.8e-5. Every top-1 token still matches with both. The numbers are bit-identical on the desktop and `gx10-03`.

## GPU path

Every Q8_0 matmul runs on the GPU: attention Q/K/V/O, the expert FFNs, and the LM head (`csrc/cuda/kernels.cu`, one warp per output row, loaded through the CUDA driver API). Norms, rotary embeddings, attention scores, and routing stay on the CPU. On GB10 the loaded weights are registered in place (0.12 s for 3.42 GB, no copy); on the RTX 5070 Ti they are copied to device memory. The GPU context is created before the weights are loaded, because with the co-tenant's vLLM holding 100.6 GB of GB10's memory, creating it afterwards failed with "out of memory".

`TF_GPU_CHECK=1` recomputes every GPU matmul on the CPU: no output differed by more than 1e-3 across a full run on GB10.

**One unexplained failure:** the first GPU run on `gx10-03` failed prompt 2 (7 of 17 top-1, 13 s instead of 0.7 s), apparently with NaNs, which the old error check ignored (it now counts any NaN as a failure). The next 10 runs on `gx10-03` and 5 on the desktop all passed. It was the first run after the build, with about 13 GB of memory free next to the co-tenant; the cause is not known.

Co-tenant on `gx10-03`: vLLM resident (100.6 GB of GPU memory), GPU 0%, load average about 0.3.
