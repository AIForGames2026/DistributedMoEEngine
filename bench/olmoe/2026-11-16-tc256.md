# Tensor-core attention for 256-dim heads (TASK-29 follow-up, 2026-11-16)

Qwen3.6-35B-A3B's 10 attention layers have 256-dim heads. Their f32 GPU kernel reached about 1.3 TFLOPS, so at 128k it took 1,074 of the 1,253 s to the first token (`2026-11-16-qwen35.md`). A new kernel, `tf_attention_tc256` in `csrc/cuda/kernels.cu`, runs it on the tensor cores the way the 128-dim kernels do: each f32 input is split into two f16 parts, and three mma products per step keep results close to f32.

How it fits:

- **Two warps per 16 query rows.** A warp holding a whole 256-dim row would need about twice the registers the 128-dim kernel uses. Instead, each warp of a pair holds half the dimensions of the queries and of the output.
- **The pair adds their partial scores.** After the score products, both warps write their partial scores to shared memory (over the keys, which are no longer needed), add the other's, and take the same softmax. Each then multiplies by its half of the values.
- **Size:** 64 query rows per block of 256 threads, 32 cache positions per tile, and 67.6 KB of shared memory for the keys and values in two f16 parts each.
- **Every KV format** (f32, bf16, fp8, bf16_fp8) gets its own copy, like the other attention kernels.
- **It is the default for every row count.** It also beats the f32 kernel for decode, because it reads the cache faster (167 GB/s against 129 GB/s at 262k). `TF_ATT_KERNEL` 1, 2 or 5 picks the f32 kernel instead.
- **`attbench --hd 256`** times both kernels and reports how far the tensor-core output is from the f32 one.

Raw logs, the script that ran them, and versions are in [`2026-11-16-tc256/`](2026-11-16-tc256/). Setup: `gx10-02`, kernel 7.0.0-1019-nvidia, driver 580.178.04, Zig 0.17.0, engine build `v0.2.0-alpha-32-gc0f7c0a-tc256`, nothing else running.

## The kernel alone (`attbench.log`)

Qwen3.6's shape: 16 query heads, 2 KV heads, random data, best of 3 runs.

| Run | f32 kernel | Tensor cores | Speedup | Tensor cores against f32 |
|---|---|---|---|---|
| 2,048 new tokens, empty cache | 20.8 ms | 3.5 ms (9.9 TFLOPS) | 6.0x | 5.3e-7 |
| 2,048 new tokens after 16,384 | 438 ms | 49.7 ms (11.8 TFLOPS) | 8.8x | 1.4e-6 |
| 2,048 new tokens after 65,536 | 1,673 ms | 190 ms (11.7 TFLOPS) | 8.8x | 2.7e-6 |
| 2,048 new tokens after 129,024 | 3,526 ms | 410 ms (10.7 TFLOPS) | 8.6x | 3.6e-6 |
| 2,048 new tokens after 260,096 | 7,082 ms | 818 ms (10.7 TFLOPS) | 8.7x | 5.7e-6 |
| 1 new token after 129,024 | 4.19 ms | 3.17 ms | 1.3x | 4.4e-8 |
| 1 new token after 262,000 | 8.35 ms | 6.41 ms | 1.3x | 6.2e-8 |

With compact caches after 65,536 positions, the tensor-core kernel takes 178 ms (bf16), 206 ms (fp8) and 189 ms (bf16_fp8), within 1.9e-6 of the f32 kernel on the same cache. The 128-dim kernels time as before (tensor cores 128 rows: 34.7 ms after 16,384 positions, 16.8 TFLOPS).

## Against transformers and the CPU

- **The TASK-24 golden check on the GPU (`golden-gpu.log`)** gives the same result as before the change:
  - Logits are within 5.34e-5, every prompt top-1 is the same, all 12,480 routing choices match, and all 96 generated tokens equal `generate()`'s.
  - It still reports `GenerateMismatch`, for the one step where transformers' own router has an exact tie (0.335, explained in `2026-11-16-qwen35.md`).
- **Against the CPU on a 2,048-token prompt (`gpucheck-*.log`):**
  - All 32 generated tokens are the same, and logits differ by up to 0.0787. The f32 kernel gave 0.0782 in the same check, so the new kernel adds no measurable difference.
  - Where that difference comes from is still not isolated.

## Speed on `gx10-02`

The same runs as `2026-11-16-qwen35.md`: the repository's text as Qwen3.6 tokens, prefilled in 2,048-token chunks, then greedy decode.

| Context | First token, f32 kernel | First token, tensor cores | Attention's share | Decode, f32 kernel | Decode, tensor cores | Peak memory |
|---|---|---|---|---|---|---|
| 2,048 | 3.05 s | 2.91 s | 0.1 s | 32.1 tokens/s | 33.3 tokens/s | 37.2 GB |
| 32,640 | 109.4 s | 52.3 s | 8.3 s (was 65.6 s) | 24.6 tokens/s | 26.4 tokens/s | 38.0 GB |
| 131,040 | 1,252.7 s | 305.2 s | 128.5 s (was 1,074.2 s) | 13.7 tokens/s | 16.1 tokens/s | 42.0 GB |
| 262,112 | 4,845.5 s | 889.8 s | 532.4 s (was 4,489.1 s) | 8.67 tokens/s | 10.55 tokens/s | 47.2 GB |

- **The whole native context** now prefills in under 15 minutes instead of 81.
- **At 128k** the first token comes 4.1 times sooner, and sooner than Qwen3-30B-A3B's 520 s.
- **What prefill time goes to now:** up to 128k, the Gated DeltaNet layers (78.6 s at 128k) and the experts (73.8 s) take about as long as attention. Both grow linearly with the prompt, so attention leads again past that (532 s of 890 at 262k).
