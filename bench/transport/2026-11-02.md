# Two-process MoE and close-path fix (2026-11-02)

PoC core check (see [POC.md](../../POC.md)). `dispatch --moe` (ReleaseFast) splits the tiny synthetic MoE from `tests/golden/moe_tiny.tfref` (2 layers, 8 experts, top-2, d_model 32, 16 tokens) across two processes: rank 0 runs the norms, router, and LM head; rank 1 runs every expert FFN. Each (token, expert) pair is one 7,552-byte dispatch packet and one combine packet carrying float32 values. Rank 0 checks routing, per-layer hidden states, and logits against the PyTorch goldens. 64 slots per ring.

|---|---|---|---|---|---|---|
| Shared memory, WSL2 desktop | x86_64 | 64/64 identical | 3.58e-7 / 4.77e-7 | 7.15e-7 | 16/16 | 0.63 ms |

| Shared memory, `gx10-03` | aarch64, `-Dcpu=cortex_a78` | 64/64 identical | 3.58e-7 / 4.77e-7 | 7.15e-7 | 16/16 | 0.93 ms |
| TCP, desktop router to `gx10-03` expert (Tailscale relay) | both | 64/64 identical | 3.58e-7 / 4.77e-7 | 7.15e-7 | 16/16 | 556 ms (342 + 214 ms per layer) |

Errors are against the PyTorch float32 reference (tolerance: atol 1e-5 + rtol 1e-4; TASK-10 target 1e-2). Results are bit-identical across paths, since the transport carries exact float32 bits and both ranks sum in the reference's order.

Co-tenant on `gx10-03`: vLLM resident, GPU 0%, load average 0.16.

## Close-path bug found and fixed

The first desktop-to-Spark MoE run passed on the router, but the expert on `gx10-03` exited with `tcp recv: peer closed with 0 of 8 bytes read`. The plain packet test (`--packets 256`) failed the same way, so this was already in `v0.1.0-poc`: the earlier runs checked only the router's output, and CI's bare `wait` ignored the expert's exit code.

Cause: both ranks sent their goodbye and then closed, so each goodbye could be the last thing before a FIN. The relayed path drops those bytes (the Oct 27 run lost the final combines the same way). Fix (`Endpoint.finish`, `tcp.Link.closeAfterPeer`): rank 0 says goodbye first; rank 1 answers only after hearing it and closes only after rank 0 has closed. No data either side still needs is ever right before a FIN.

| Run after the fix, desktop to `gx10-03` | Router exit | Expert exit |
|---|---|---|
| `--moe` x 4 | 0 | 0 |
| `--packets 1024` (5.1 s, 5,017 µs per token, relay-bound) | 0 | 0 |
| `--packets 512` x 3 | 0 | 0 |

One `--packets 1024` attempt right after the fix failed on the router with `ConnectionClosed` after all 1,024 combines arrived, while the expert's log showed no connection on that port. It did not recur in the 8 runs above; cause unknown, logged here in case it returns.

CI now runs the shared-memory and TCP loopback checks in both modes and fails if either process exits non-zero.

## Cross-compile note

Plain `-Dtarget=aarch64-linux-gnu` targets baseline ARMv8.0, which has no CRC32C instructions, so `tf_crc32c` falls back to bitwise code: 44 µs per token over shared memory on `gx10-03`, against 1.8 µs for a native build. With `-Dcpu=cortex_a78` (ARMv8.2; GB10's Cortex-X925/A725 cores are a superset) it is 3.1 µs. Release binaries use that flag.
