# Prefill and decode speedups after TASK-12, Nov 11

Same setup as [the TASK-12 runs](2026-11-11-long-context.md): Qwen3-30B-A3B (Q8_0) on `gx10-02`'s GB10 with `--gpu --yarn 4`, the repository's own text as the prompt, 2,048-token chunks. Scripts and logs are in [`2026-11-11-speedups/`](2026-11-11-speedups/):
- `run.sh` first;
- then `after.sh`, which was stopped during its 128k run (see Notes);
- `final.sh` on the final build;
- `router.sh` with the decode router moved back to the CPU, the last change.

## Results

|---|---|---|---|
| 16k, time to first token | 95.7 s | 21.0 s | 4.6x |
| 16k, decode | 0.079 s per token | 0.047 s per token | 1.7x |
| 128k in RAM, time to first token | 1,918 s | 540.1 s | 3.6x |
| 128k in RAM, decode | 0.230 s per token | 0.191 s per token | 1.2x |
| 128k offloaded, time to first token | 1,947 s | 574.0 s | 3.4x |
| 128k offloaded, decode | 3.83 s per token | 3.76 s per token | bound by the drive |

"Before" is the build that recorded TASK-12 (at 16k, after its router and expert changes). The 16k rows are from `router.sh`; the 128k rows are from `final.sh`, before the decode router went back to the CPU. That change saves about 10 ms per token, which matters little at 128k.

Offloaded runs still match all-RAM runs bit for bit: at 128k on `final.sh`'s build, and at 16k on both builds. The Qwen3 goldens pass on the last build:
- logits within 1.87e-4 (2.65e-4 before);
- top-1 37/37, and every routing choice identical;
- all 3 x 32 YaRN tokens match transformers' `generate()`.

## The changes

- **Tiled matmul** (`tf_mm_q8`, `tf_mm_f32`). Each block computes 128 weight rows for 64 inputs, and each thread keeps 8 rows by 4 inputs in registers, so a weight is read once per 64 inputs instead of once per 8. Sums still run in column order in f32. The same kernel takes a whole layer of experts in one launch, one grid slice per expert.
- **Decode matmul** (`tf_mv_q8`, `tf_mv_q8_gateup`). For up to 8 inputs per matrix, one warp per row reads half a Q8_0 block per lane, so a warp reads 16 blocks per step. In decode, an expert's gate and up matmuls and SiLU are one pass over both weights.
- **Experts as one call per layer, end to end.** The token rows go to the GPU once (n x d instead of n x 8 x d), a kernel gathers each expert's inputs, and another adds up each token's 8 weighted outputs in a fixed order. Only n x d comes back. Calls are grouped by expert with a counting sort. With a GPU, decode uses this path as well: one call per layer instead of 8.
- **q, k and v in one call** (`tf_gpu_matmuls`): one copy in, three kernels, three copies out.
- **Router on the GPU** for prefill, with the f32 tiled kernel. For 8 tokens or fewer it stays on the CPU: on the GPU, one token's router was a single 128-row block and cost about 10 ms per decode step.
- **Tensor-core attention** for prefill (`tf_attention_tc128`, and `tf_attention_tc` for 64 to 127 query rows per KV head). Every f32 input (queries, keys, values, and probabilities) is split into a high and a low f16 part, and each product adds three mma results: high by high, high by low, and low by high. On OLMoE with this kernel forced everywhere, the goldens show why each part is needed:
  - plain f16 inputs moved the logits from 5.5e-5 to 7.1e-3 off transformers, and generation failed (0.63);
  - dropping only the low part of the probabilities gave 1.6e-3, and generation failed (0.38);
  - with all three products, the logits stay at 6.8e-5, like the f32 kernel.

  On the desktop GPU, removing products made the kernel no faster.
- **Decode attention** (`tf_attention_decode8` and `16`, up to 16 query rows per KV head). Each lane scores one cached position for every row, then the warp adds up the values in coalesced 512-byte rows. Exact f32, about 9e-9 from the wide kernel.
- **CPU side.** A persistent thread pool (`src/pool.zig`) replaces spawning threads per matmul. In long passes, `step` splits its per-token loops across it: norms, QK norm and rope, residual adds, and softmax with top-k. Rope's cos and sin are computed once per position and step instead of twice per layer. Each token comes out exactly as on one thread.

`TF_MM_KERNEL=1` brings back the first matmul kernel, and `TF_ATT_KERNEL` picks an attention kernel (1 first, 2 wide, 3 tensor cores with 64 rows, 4 with 128, 5 decode).

## Attention kernels on GB10

`attbench` (`attbench-final.log`), per layer, for a 2,048-token chunk after the given number of cached positions:

| Cached positions | Wide (f32) | Tensor cores, 64 rows | Tensor cores, 128 rows |
|---|---|---|---|
| 16,384 | 75.8 ms | 43.4 ms | 35.4 ms |
| 129,024 | 638.0 ms | 365.6 ms | 300.2 ms |

Their outputs are within 3.6e-6 of the wide kernel's (the wide and first f32 kernels differ by 4e-8). For one new token after 131,071 positions, the decode kernel takes 3.22 ms against the wide kernel's 3.54 ms. Every kernel there reads the cache at 150 to 170 GB/s, well short of GB10's 273 GB/s, so decode at long context is still bound by memory reads. On the desktop's RTX 5070 Ti, the decode kernel reached 717 GB/s, 1.9x the wide kernel.

## How far the tensor cores move long-context results

At 16k (`drift-*.log`), all 8 generated tokens are identical with every kernel. Taking the wide f32 kernel throughout as the reference:
- the first f32 kernel, which only adds in a different order, moves the generated tokens' logits by up to 0.20;
- the final build's kernels move them by up to 0.85.

Small per-step differences grow over 48 layers and 16k positions, so long-context logits are sensitive even to the order of sums. The tensor cores add about 4x that. There is no transformers reference at this length. `TF_ATT_KERNEL=2` keeps prefill attention in f32 for runs that need it, at 28.0 s for the 16k prefill instead of 21.0 s.

## Notes

- The first 128k pair (`run.sh`, before the decode kernel and 128-row blocks) took 636.1 s in RAM and 670.0 s offloaded to the first token, with decode at 0.203 and 3.682 s per token, and the offloaded run matched bit for bit.
- `after.sh` was stopped during its 128k run, and a leftover copy of that run overlapped the first try of `final.sh`. Both were stopped and `final.sh` was run again alone; only that run's logs are kept.
- Not done: CUDA graphs and keeping a whole layer's activations on the GPU. Each layer still makes about five calls that copy in and out, which matters little next to attention at long context.
- Next steps. Prefill attention at 128k: fewer tensor-core products would need a cache format with less to round, which is TASK-27's area. Experts: tensor cores could take the Q8_0 weights as exact f16 integers, with inputs split in two (2 products instead of 3).
