# Qwen3.6-35B-A3B, a hybrid linear-attention model (TASK-29, 2026-11-16)

The engine now runs Qwen3.6-35B-A3B (transformers' `qwen3_5_moe`, GGUF architecture `qwen35moe`): ggml-org's [Q8_0 GGUF](https://huggingface.co/ggml-org/Qwen3.6-35B-A3B-GGUF), 36.9 GB, SHA-256 checked against Hugging Face.

The model is a hybrid of 40 layers:

- **30 Gated DeltaNet layers** (three of every four): a linear attention with a fixed-size state per layer.
  - A causal depthwise convolution (4 taps) with SiLU runs over the query, key and value projections.
  - Queries and keys are L2-normalized. Each of 32 value heads keeps a 128 x 128 matrix that decays and is corrected toward the new value token by token (the gated delta rule).
  - The output goes through an RMSNorm gated by SiLU of a second projection.
- **10 attention layers:**
  - 16 query heads and 2 KV heads of 256 dimensions.
  - An output gate that comes with the query projection.
  - Rotary embeddings on the first 64 dimensions of each head.
- **Every MoE block:** 8 of 256 experts plus a shared expert, scaled by a sigmoid gate.

What changed:

- **Model:** `src/olmoe.zig` reads the layer mix from the GGUF. `recurrentMix` runs the Gated DeltaNet in llama.cpp's layout. In that layout value heads are tiled, so head h reads key head h mod 16, and `ssm_a` already holds -exp(A_log).
- **KV cache:** it holds keys and values for the 10 attention layers only, plus each Gated DeltaNet layer's state (65.9 MB in all, whatever the length).
- **GPU:**
  - A new attention kernel for 256-dim heads, in all four KV formats (TASK-27).
  - A delta-rule kernel: one block per value head, each thread holding one column of the state in registers.
  - The convolution, normalizations and gates stay on the CPU.
- **Tokenizer:** the `qwen35` pre-tokenizer (`src/tokenizer.zig`) is Qwen3's with combining marks counted as letters. On 528 texts it gives exactly Hugging Face's ids (60,146 tokens), loaded from the GGUF and from `tokenizer.json` alike (`tools/ref/check_tokenizer.py`).
- **Rewinding:** a Gated DeltaNet state cannot step back. `KvCache.truncate` keeps everything or starts over, and the server's prompt reuse reports what it actually kept.
  - `--kv-offload` and `--prefix-cache` refuse this model for now, since neither saves the state.
- **Tiny test model:** `tools/ref/ref_qwen35.py --tiny` writes a tiny model with the same layer mix, and `zig build test` checks it against transformers. Every layer's hidden state, the logits, the routing and 16 generated tokens per prompt match within 1e-4.

Raw logs, the script that ran them, and versions are in [`2026-11-16-qwen35/`](2026-11-16-qwen35/).

Setup:

- `gx10-02`, kernel 7.0.0-1019-nvidia, driver 580.178.04, Zig 0.17.0, nothing else running.
- Engine build `v0.2.0-alpha-31-g59e8a5a-q35`.
- Reference: transformers 5.23.0 and torch 2.15.0 (CPU, float32, eager attention) on the GGUF's dequantized weights. `tools/ref/requirements-qwen35.txt` pins them.
- Goldens: `ref_qwen35.py --gguf Qwen3.6-35B-A3B-Q8_0.gguf --config config.json --tokenizer tokenizer.json --out qwen35_generate.tfref --generate 32`, which took 7 min 18 s and 39 GB on `gx10-02`'s CPU. The smallest router margin over the prompts is 5.2e-7.

## Against transformers (TASK-10 and TASK-24 checks)

These are the three TASK-24 prompts (5, 19 and 15 tokens), then 32 greedy tokens each.

| Run | Worst logits error | Prompt top-1 | Routing choices the same | Generated tokens equal to `generate()` | Logits error while generating |
|---|---|---|---|---|---|
| One process, CPU | 4.58e-5 | 39 of 39 | 12,480 of 12,480 | 96 of 96 | 5.20e-5, except one step (below) |
| One process, GPU | 5.34e-5 | 39 of 39 | 12,480 of 12,480 | 96 of 96 | 5.44e-5, except one step |
| Two processes, shared memory | 4.39e-5 | 39 of 39 | 12,480 of 12,480 | 96 of 96 | 4.96e-5, except one step |
| Two processes, RDMA | 4.39e-5 | 39 of 39 | 12,480 of 12,480 | 96 of 96 | 4.96e-5, except one step |

The two-process runs send activations in f32 (`--payload f32`). Rank 1 ran 27,008 of the 54,720 expert calls.

The default FP8 activations move the logits by up to 1.17 and change 243 of 12,480 routing choices, but no top-1 token (`fp8/`).

**The one step that differs is an exact tie in the reference.**

- At generated token 3 of prompt 1, every run's logits differ from `generate()`'s by 0.335 while the token stays the same.
- A diagnostic run of transformers alone found the cause.
  - At that step its router has an exact tie in layer 38: the 8th and 9th expert probabilities are equal, a margin of 0.0.
  - Transformers' own full forward pass over the same tokens gives logits 0.335 away from its `generate()` at that step, and within 3e-5 elsewhere before it.
- So the engine follows one side of a tie that transformers itself resolves two ways.
- The other 95 steps match within 5.4e-5, and every token matches.
- Because of this one step, the golden check reports `GenerateMismatch` for every run.

## The GPU's kernels against the CPU's

On a 2,048-token prompt from `repo.tokens` plus 32 generated tokens, the run with attention and the delta rule on the GPU produces exactly the CPU run's 32 tokens. Logits differ by up to 0.078 through them (`gpucheck-*.log`). I have not isolated where that difference comes from. The GPU and CPU runs each match transformers within 5.4e-5 on the short prompts above.

## Speed on `gx10-02`

The prompt is the repository's own text tokenized with Qwen3.6's tokenizer (`repo.tokens`, 467,993 tokens from 83 files), prefilled in 2,048-token chunks, then greedy decode. The native context is 262,144 tokens, so no YaRN.

| Context | KV cache | First token | Prefill | Decode | Peak memory |
|---|---|---|---|---|---|
| 2,048 | 0.09 GB | 3.05 s | 671 tokens/s | 32.1 tokens/s | 37.2 GB |
| 32,640 | 1.34 GB | 109.4 s | 298 tokens/s | 24.6 tokens/s | 38.0 GB |
| 131,040 | 5.37 GB | 1,252.7 s | 105 tokens/s | 13.7 tokens/s | 42.0 GB |
| 262,112 | 10.74 GB | 4,845.5 s | 54 tokens/s | 8.67 tokens/s | 47.2 GB |

The KV cache takes 40,960 bytes per token, 4.8 times less than Qwen3-30B-A3B's 196,608, because only 10 of 40 layers keep keys and values. So decode at 128k runs 2.5 times faster than Qwen3-30B-A3B's 5.56 tokens/s (`2026-11-16-kv-formats.md`), without a compact format.

The 262,112-token run uses the whole native context in 47.2 GB. Prefill is slower than Qwen3-30B-A3B's (520 s to the first token at 128k). Of the 1,253 s at 128k, 1,074 s are attention: the 256-dim kernel uses plain f32 arithmetic and reaches about 1.3 TFLOPS. The 128-dim kernels use tensor cores. The Gated DeltaNet layers took 79 s and the experts 74 s. A tensor-core 256-dim kernel, added the same day, brings the 128k first token to 305 s ([`2026-11-16-tc256.md`](2026-11-16-tc256.md)).

Two fixes on the way, both visible in the logs' time breakdowns:

- **Convolution order:** the convolution first ran channel by channel, reading its input at a 32 KB stride. Running it token by token cut its share of a 2,048-token prefill from about 10 s to a fraction of a second.
- **Buffer reuse:** each Gated DeltaNet layer and shared expert allocated fresh output buffers. Copying GPU results into untouched pages took 16.5 s of a 2,048-token prefill (Nsight Systems). They now reuse one set per step, and the 2,048-token first token went from 19.4 s to 3.1 s.

## Golden regenerated with router gaps (Nov 18)

From TASK-31 on, the generation check excuses a step whose logits miss 1e-2 when transformers' own router had a near-tie there (gap below 1e-6), but it reads those gaps from the golden (`prompt{p}.gen_gaps`), and this golden was made before them. So prompt 1's step 3, the exact tie above, failed the check with every build since.

- `ref_olmoe.record` (shared by `ref_qwen35.py`) takes `gaps=True` to record each generated step's smallest gap between the k-th and (k+1)-th router probability over all layers, as `ref_qwen38.py` does. Only `ref_qwen35.py`'s real-model run turns it on, so the tiny goldens are unchanged (`ref_qwen35.py --tiny --check` still matches).
- Rerun on `gx10-02` with transformers 5.23 (`ref-venv5`): 7 min 57 s, 39.6 GB (`2026-11-16-qwen35/reference-gaps.log`). Every tensor of the new file is identical to the old one's; the only additions are the three prompts' gaps. Prompt 1's step 3 has a gap of exactly 0; steps below 1e-6 are 3, 4, 5, 10, 19 and 23 of prompt 1 and 12, 25, 26 and 29 of prompt 2.
- `olmoe local ... --golden qwen35_generate.tfref --generate 32 --gpu` now passes, with step 3 reported as a near-tie and its logits held up to there (`2026-11-16-qwen35/golden-gaps.log`). The old file stays on `gx10-02` as `qwen35_generate_nogaps.tfref`.

Unrelated, found while checking: `ref_olmoe.py --tiny --check` and `ref_qwen3.py --tiny --check` report a mismatch on `gx10-02` with the committed scripts as well, the GGUF files included, so the tiny files there were made with other library versions; the engine's tests on them still pass.
